# LK-11 Observability dan Dashboard

Pemantauan model rain-risk-classifier (LK-10) dengan Prometheus dan Grafana, ditambah deteksi data drift sederhana.

## Arsitektur
klien -> gateway (FastAPI + prometheus_client, host 8090) -> nginx -> 3 replika model-serving (LK-10).
Prometheus men-scrape gateway tiap 5 detik. Grafana membaca Prometheus (data source dan dashboard di-provision dari berkas).

Mengapa gateway: image hasil `mlflow models build-docker` tidak punya `/metrics` (HTTP 404, terbukti), dan hanya lapisan aplikasi yang melihat isi request (distribusi prediksi dan drift). nginx menambah header `X-Upstream` agar gateway tahu replika mana yang melayani.

## Cara menjalankan
1. Jalankan stack LK-10 sampai model-serving (3 replika), nginx, dan mlflow-server hidup (lihat dokumentasi LK-10; registry Compose lokal harus berisi alias production).
2. `python monitoring/make_baseline.py` (mean dan std tiap fitur dari X_train, tulis `monitoring/baseline.json`).
3. `docker compose up -d --build gateway` lalu `docker compose restart nginx prometheus`.
4. Trafik referensi (mengisi `positive_rate` baseline), lalu restart gateway:
   `python monitoring/send_traffic.py --source train --n 300 --seed 1 --save-positive-rate && docker compose restart gateway`
5. Buka Prometheus `:9090` (Status > Targets: job gateway UP) dan Grafana `:3000` (dashboard "Rain Risk - Observability (LK-11)"). Login admin, sandi dari `GRAFANA_ADMIN_PASSWORD` (default `admin`, hanya demo lokal).
6. Beban: `python monitoring/send_traffic.py --source train --n 3000 --concurrency 4 --seed 32`.
7. Simulasi drift: tambah `--shift hu=15 --shift t=-3`.
Dashboard dibuat oleh `monitoring/make_dashboard.py` (keluaran: `monitoring/grafana/provisioning/dashboards/rain-risk.json`).

## Metrik (gateway, port 8000 di dalam jaringan, 8090 di host)
| Metrik | Makna |
|---|---|
| `rr_requests_total{status}` | Jumlah request /invocations per kode HTTP. Dasar throughput dan error rate. |
| `rr_request_latency_seconds` (histogram) | Latensi end-to-end gateway -> nginx -> replika. p50/p95/p99 via `histogram_quantile`. |
| `rr_predictions_total{label}` | Jumlah prediksi per kelas (0 tidak berisiko, 1 risiko hujan). Distribusi prediksi. |
| `rr_upstream_requests_total{upstream}` | Request per replika (dari header X-Upstream). Bukti distribusi trafik. |
| `rr_positive_rate_window` / `_baseline` | Rasio prediksi 1 pada jendela 200 prediksi terakhir vs baseline. |
| `rr_window_size` | Jumlah baris di jendela (drift dihitung jika >= 30). |
| `rr_feature_window_mean`, `rr_feature_baseline_mean` | Mean fitur jendela vs baseline (X_train). |
| `rr_feature_drift_d{feature}` | d = (mean jendela - mean baseline) / std baseline. Satuan: simpangan baku baseline. |
| `process_cpu_seconds_total`, `process_resident_memory_bytes` | CPU dan RAM proses gateway (bawaan prometheus_client). |

## Cara membaca drift
- d = 0 berarti mean fitur di jendela sama dengan baseline. |d| = 1 berarti rata-rata bergeser satu simpangan baku baseline.
- Yang dibandingkan adalah mean 200 request terakhir, bukan nilai tunggal, sehingga noise sampling kecil (galat standar teoretis sekitar 1/sqrt(200) = 0,07).
- Selisih rasio prediksi = |rasio 1 jendela - rasio 1 baseline|.
- Drift fitur adalah proxy karena label asli (hujan terukur) tidak tersedia saat inferensi (ground truth delay).

## Justifikasi threshold (diukur, bukan ditebak)
Kalibrasi pada trafik normal: 8 run x 200 baris acak dari X_train (seed 11-18).
- max |d| antar 11 fitur per run: 0,057 sampai 0,167 (tertinggi 0,167, ws_lag1).
- Rasio prediksi 1 per jendela: 0,305 sampai 0,405 (baseline 0,343); simpangan terbesar 0,062.

| Sinyal | WARNING | CRITICAL | Alasan |
|---|---|---|---|
| max abs(d) | > 0,25 | > 0,5 | WARNING sekitar 3,5x galat standar dan 1,5x di atas maksimum normal teramati (0,167): jarang alarm palsu. CRITICAL sekitar 7x galat standar. |
| selisih rasio prediksi 1 | > 0,10 | > 0,15 | Sekitar 3x galat standar binomial (0,034); maksimum normal teramati 0,062. |
Ambang sengaja di atas noise untuk menghindari alert fatigue. Pada implementasi ini ambang tampil sebagai warna stat dan garis pada panel Grafana; tidak ada Alertmanager atau notifikasi.

## Hasil
- Beban: 3 replika menerima trafik merata (sekitar 10 req/s masing-masing pada total 29,5 req/s), error rate 0%. Concurrency 4: 30,6 req/s, p50 klien 129 ms. Concurrency 8: 31,0 req/s, p50 klien 239 ms, p95 513 ms (throughput tidak naik, latensi naik: tanda saturasi; penyebab diduga 1 worker per replika di mesin 2-core, belum diuji).
- docker stats saat concurrency 8: replika model 44-66% CPU dan sekitar 313-318 MiB dari 768 MiB; gateway 12% CPU dan 43 MiB.
- SIMULASI drift (bukan drift nyata): hu +15, t -3 pada sampel train. d(t) = -0,752 dan d(hu) = +0,692 (run seed 52); puncak di dashboard sampai 0,95. Sembilan fitur lain tetap < 0,06. Setelah trafik normal kembali, |d| turun di bawah 0,25.
- Drift prediksi pada simulasi yang sama lemah dan tidak konsisten: selisih 0,032 (seed 52), tetapi sempat 0,122 pada run lain. Artinya memantau output saja bisa meloloskan pergeseran input.
- Drift alami: split train.py terbukti kronologis (train 28 Sep - 9 Okt, test 9 - 13 Okt, 30 kelurahan di keduanya). Sampel X_test memberi d(tcc) = +0,371, d(ws_lag1) = -0,259, d(ws) = -0,245, di atas maksimum trafik normal (0,167) dan melewati WARNING: pergeseran antar periode pada data BMKG terdeteksi.

## Analisis: mendeteksi model decay
Label hujan baru diketahui belakangan (ground truth delay), jadi performa tidak bisa dihitung langsung. Dashboard memantau proxy:
1. Drift fitur input (mean vs baseline dalam satuan std). Jika |d| melewati 0,25 (WARNING) atau 0,5 (CRITICAL), distribusi input sudah berbeda dari data latih dan akurasi model patut diragukan (data drift).
2. Distribusi prediksi (rasio kelas 1 vs baseline). Pergeseran besar menandakan prediction drift atau perubahan perilaku model. Sinyal ini lebih lemah dari drift fitur pada simulasi kita.
3. Latensi, throughput, error rate, dan CPU/RAM mendeteksi kegagalan operasional. Latensi saja tidak cukup: model bisa cepat dan tetap salah (silent failure).
Penurunan performa diduga bila sinyal 1 atau 2 bertahan di atas ambang pada beberapa jendela berturut-turut, bukan satu lonjakan. Hasil ini bisa menjadi pemicu continuous training (LK-12). Dashboard tidak bisa membuktikan penurunan recall; konfirmasi memerlukan label.

## Keterbatasan
- Drift diuji dengan simulasi: hanya kolom yang disebut yang digeser (fitur turunan seperti hu_lag1 dan rolling mean tidak ikut).
- Kalibrasi threshold dari 8 run i.i.d. sampel train plus perhitungan teoretis; bukan data produksi.
- Jendela berbasis jumlah request, bukan waktu. Saat tidak ada trafik, gauge drift menahan nilai terakhir (tidak disegarkan).
- Baseline dan positive_rate memakai sampel train (model pernah melihatnya); rasio prediksi 1 baseline (0,343) lebih tinggi dari rasio hujan asli 22,1% (dugaan: class_weight balanced dan prioritas recall).
- CPU/RAM per kontainer: cAdvisor dicoba tetapi gagal di Codespaces (log: Failed to create existing container, hanya metrik host tampil; diduga terkait containerd image store) dan dicabut. Bukti per kontainer memakai `docker stats`; dashboard hanya menampilkan CPU/RAM proses gateway.
- Label adalah turunan prakiraan BMKG, bukan hujan terukur.
